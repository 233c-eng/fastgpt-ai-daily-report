# 📰 FastGPT 多 Agent AI 行业日报系统 
> 基于 FastGPT 左转流程编排引擎构建的六节点多 Agent 协作流水线，实现每日 08:00（北京时间）无人值守自动产出可溯源的 AI 行业深度日报，并推送至飞书群。

## ✨ 项目亮点

- **六节点流水线**：采集 → 清洗 → 聚合 → 核查 → 成稿 → 分发，职责单一、可独立调试
- **架构级反幻觉**：链接原值直通 + 禁止补充输入外事件 + 可验证性三级评级，内容 100% 可溯源
- **无人值守交付**：定时触发 + 时区校准 + 飞书 Webhook 推送，零人工干预稳定运行
- **踩坑驱动开发**：完整记录变量断链、时区偏差等真实调试过程，附解决方案

## 🏗️ 架构
```mermaid
graph LR
    A[⏰ 定时触发 08:00] --> B[HTTP: 天行资讯API]
    B --> C[代码运行: 格式化清洗]
    C --> D[🕵️ 信息猎手]
    D --> E[🔍 事实核查员]
    E --> F[📝 执行总编]
    F --> G[📨 飞书Webhook推送]
```
### 数据流说明

1. **定时触发**（FastGPT 定时执行配置）：每日 08:00，时区 Asia/Shanghai
2. **数据采集**：HTTP 请求节点调用天行资讯 API，获取原始资讯
3. **格式化清洗**：代码运行节点统一字段（标题/摘要/链接/来源/发布时间），下游 LLM 只处理干净结构化数据
4. **信息猎手**：执行 30 天时间窗过滤、发布时间倒序、链接原值直通硬约束，输出 8-12 条资讯列表
5. **事实核查员**：可验证性三级评级（高/中/低）+ 存疑原因标注，禁止补充输入外事件
6. **执行总编**：产出导语 + 热点 TOP5（创业者/投资人/从业者三视角）+ 全量事件概览表

## 🚫 反幻觉设计（核心）

大模型生成日报最大的风险是「编造新闻和链接」。本系统从**架构层面**而非提示词层面解决：

| 防线 | 机制 |
|---|---|
| 第一道 | 链接字段**原值直通**：链接不经过 LLM 之手，从数据源原封不动流转至最终输出 |
| 第二道 | 提示词硬约束：「禁止生成数据源中不存在的链接/事件」+ 空数据时明确回复「无资讯」 |
| 第三道 | 独立事实核查员节点，对每条资讯标注可验证性等级与存疑原因 |

## 附录：工程踩坑纪实（Bug Log）

记录真实调试过程中遇到的各种“隐性故障”与应对规范。多 Agent 流水线的可靠性 = 模型聪明 + 约束显式 + 引用链闭环 + 故障显性化。

## 🕳️ 踩坑记录（真实调试过程）
### 坑 1：事实核查员输出「无待核查资讯」

- **现象**：流水线跑通后，核查员永远回复查不到内容，但上游明明有产出。
- **原因**：核查节点引用了空变量，而非「信息猎手 > 新的上下文」——**输入断链**。
- **教训**：多节点流水线中，断链不一定报错，模型会礼貌地编个「没数据」回应你。每个节点的输入来源必须逐个验证，不要相信「看起来在跑」。

### 坑 2：定时任务时区陷阱

- **现象**：定时配置默认时区为 (UTC-10) Pacific/Honolulu，填 8:00 后实际触发时间偏离预期。
- **原因**：系统按配置时区执行，UTC-10 的 8:00 = 北京时间凌晨 2 点。
- **解决**：显式配置 Asia/Shanghai，并用「几分钟后」短周期试跑校准实际触发时间，再正式上线。
- **教训**：调度系统的时间问题不能靠猜，试跑验证 > 理论配置。
### 坑 3：飞书机器人收到的消息是一堆 `#` 和星号

**现象**：日报在 FastGPT 对话页里排版精美，推到飞书群后 Markdown 语法全部原样显示。

**原因**：飞书自定义机器人的 `text` 消息类型不解析 Markdown，需要用 `post`（富文本）消息类型，且语法与标准 Markdown 不同（链接格式为 `[标题](链接)` 写在 text 字段里，加粗用 `**` 不生效）。

**解决**：对推送内容做了两处适配——
1. 标题层级降级：`#` 大标题改为「【】」包裹的纯文本样式
2. 表格改为竖排列表：Markdown 表格在飞书中无法渲染，改为逐条罗列

**教训**：推送渠道的消息格式是「下游契约」，内容生成端（LLM 提示词）必须与推送端约定一致的输出格式，否则用户看到的将是半成品。
### 坑 4：报头日期是模型瞎编的
- **现象**：数据明明是 9 月的，日报报头每次输出不同日期，还写错过年份月份。
- **原因**：LLM 没有可靠的"今天"概念，Prompt 里没规定日期来源，模型自由发挥。
- **解决**：铁律①——报头日期必须取素材中最新一条的 publish_date，禁止自行推测。
- **教训**：凡是模型"应该知道"的环境信息（日期、时区、当前状态），都要显式给来源，日期跟随数据走。

### 坑 5：下游节点擅自抬高上游的风险评级
- **现象**：核查员标"可验证：低"（★★），总编输出成★★★★★，且"存疑说明"被静默删除。
- **原因**：下游 LLM 倾向于"写得更丰富"，擅自美化评级、丢弃风险标注，误导读者。
- **解决**：铁律②——星级沿用上游评级禁止上调 + 存疑说明以"⚠️ 可信度提示："原样透传；写作要求里加兜底条款。
- **教训**：多 Agent 流水线中，风险标注必须"锁死"在链路上传递，不能指望每个节点都诚实转述。

### 坑 6：元数据逐站丢失——每个改写节点都是一次有损压缩（本次最坑）
- **现象**：日报输出"素材未提供 publish_date""素材未提供原始链接"——总编没犯错，素材到它手里已被剥光。
- **原因**：逐站回查发现，核查员输出格式没写时间字段、分析师输出格式没写链接字段。LLM 改写节点只保留自己关心的字段，输出格式里没显式要求的字段会静默蒸发。
- **解决**：核查员输出格式补"发布时间"字段；分析师加"保真铁律"强制原样保留链接和时间；总编一行不用动（它的铁律本来正确，素材补全后自动恢复）。
- **教训**：① 改写节点的输出格式必须显式列出所有需要存活的字段，且写成"禁止省略、编造、改写"；② 好的约束设计会让故障自己浮出水面——总编诚实地报"待补"而不是编造，才让这个坑被发现。

### 坑 7：代码输出了字段，提示词却拿不到
- **现象**：清洗节点日志里明明白白打印了 url 和 source，可到了执行总编节点，生成的日报里链接全是空白占位，来源字段要么空着、要么是模型自己编的媒体名。
- **原因**：字段契约断裂 —— 代码节点按自己的习惯输出 url / source，而提示词模板里写的是「引用 link / media 字段」。名字对不上，下游引用胶囊选不到正确字段，模型拿到 undefined 就开始自由发挥。
-**解决**：定一张字段契约表（title / summary / link / media / publish_date），代码节点、提示词引用、输出模板三处统一；以后改字段名必须三处同改，不允许 "代码里顺手改了个名"。
-**教训**：多 Agent 流水线里，字段名就是上下游的接口契约。菜单里能选到这个字段 ≠ 选对了字段 —— 每个引用都要用节点日志实证一次。
### 坑 8：说好的 TOP5，每天条数都不一样
-**现象**：提示词白纸黑字写着「输出热点 TOP5」，但跑出来今天 4 条、明天 6 条、偶尔还蹦出 7 条；信息猎手给的条数和总编实际写的条数对不上，概览表和正文条数漂移。
-**原因**：数量是用自然语言写在 Prompt 里的 —— 模型自由裁量：素材够就多写两条、不够就少凑两条；信息猎手、事实核查、执行总编三个节点对 "TOP5" 各自理解，谁也不严格。
-**解决**：把数量从提示词里删掉，下沉到代码节点 —— 由代码计算 top_n（按发布时间倒序、去重后硬截断到 N 条），再喂给下游；提示词只留一句「严格按给定条数输出，不多写不少写」。
-**教训**：凡代码能算的（数量、去重、排序、时间过滤），不要让 LLM 来拍板 ——LLM 只负责照抄字段和写作，自由裁量越少，输出越稳。

##🚀快速开始

1. 导入 `workflow.json` 至 FastGPT（需支持工作流编排 + 定时执行的版本）
2. 在 HTTP 请求节点替换天行 API Key（搜索 `TIANAPI_KEY_PLACEHOLDER`）
3. 在飞书推送节点替换 Webhook 地址（搜索 `WEBHOOK_URL_PLACEHOLDER`）
4. 配置定时执行：每天 08:00，时区 Asia/Shanghai
5. 发布应用，完成 ✅
